## 战胜恐惧，从一个小尝试开始

browser-bridge 这个项目的后端是 CLI + Gateway 的应用。后端几乎只转发指令到浏览器扩展程序，应用本身并没有太多的业务逻辑处理。

一开始只是觉得，每次我通过Github CI 发布之后，安装起来挺费劲。

因为，github的国内地址被污染了，导致经常出现国内的网连不上github。为了解决这个问题，我一般都是连接的公司 VPN。可是公司的VPN带宽是有限的，最高200kb/s的下载速度。而我的发布产物大概是在64MB，如果要下载就得4~5分钟，有点慢。

我之前注意力在产品功能的迭代上，没太关注这个事儿。最近一细想，发现解法可能有些复杂。

表面上看，是因为下载速度的问题。但从产品设计的意图以及系统架构上看，自己的系统设计也有很大的问题。最大的问题就在于当前构建的系统方式和设计这个系统的意图，没有匹配好。

我并不需要 CLI + 两个后端进程，这样一个既能服务与云端Agent又能服务与本地Agent的架构。我目前真正需要的是一个能服务好本地Agent的浏览器插件，云端Agent这个场景不是产品的主要服务对象。

所以，唯一的解法就是推导之前的架构，重新设计。

我很害怕，纠结。 **不甘心承认之前的方向是错的，也不敢直接使用go来替换bun。前者是不愿承认自己之前的愚蠢，后者是担心为了纠正错误而采取太过激进的方案导致又进入另一个极端。** 毕竟，go 这语言自己一点儿也不了解。

但这次假期，正好得着连续十三天的空闲。我想着，要不就拉个分支来试试？反正token不用也是要被回收的，就开始造起来呗~~

结果这次重构，出乎意料的顺利，几乎只花了一天的时间就把功能完全迁移。进程从两个变为一个，CLI也合并到这个进程中，整个包的体积从74MB变为8.8MB。功能并没有损失，只是之前的CI、Release、Devops等流程的重新配置花了些时间。

这事儿给我个教训。 **当你害怕做出选择的时候，需要仔细问自己在怕什么。如果答案是不知道，那就不用想了，直接干就完事儿了！**
