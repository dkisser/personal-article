## Agent 工具的差异化，在你不看屏幕的那几分钟

最近三天我在重构手头那个任务管理 App——切领域模型，顺手把框架层从 Electron 换成 Tauri + Node。

重构的事回头再写，这次想聊的是换工具时被改掉的一个动作。

## 以前我得盯着它

以前跑 agent，它会在某个环节停下来，等你确认一句。

它停下来的那一刻，我并不知道。因为担心错过，所以我还是坐在那儿看它刷，刷到它停。

这个动作，这次重构里我重复了几十次。

直到我把 Ghostty 和 Orca 换上来。

手机上有推送，桌面上有提醒：它要人介入的时候我会知道，它做完了我也会知道。

发呆时间就这么省出来了。只是个小细节，但它是这次换工具里我最在意的一条。

## 屏幕放下了，事还得我记着

以前建 worktree 我用的是 `claude -w xxx` 。这其实就是原生 `gh` 的封装，claude 只是把位置固定在了当前项目的 `.claude/worktrees` 里。用完还得调个 `skill` 去退出 worktree，把收尾动作走完。

每一步都得我自己记住。

Orca 把这些变成了图形化，而且可以在创建 worktree、删除 worktree 之后挂自定义脚本。

收尾那一步，不用我记着了。

到这儿我才反应过来， **它替我接过去的不是几个操作，是一堆决定** ：先决定怎么做，再决定做什么，再决定要不要做。

纯 CLI 太自由了，自由到大脑一下子就宕机。

**决定能交出去，那“什么时候来问我”是不是也能交出去？**

orchestration 这块我平时用的是 Kimi-k3 + MiniMax-M3.1-Flash-Preview 这个组合，两个 agent 接力跑。同样的任务交过去，两个 harness 的反应不一样。

Claude Code 遇到实现细节上的不确定，会弹个框问你要答案，agent 就此阻塞住，你回了它才继续。

Codex 不会。能处理的它先处理掉，剩下不确定的写进执行结果里问你，你补什么它就再做什么。

**差别落在同一个点上：谁来打断我，什么时候打断我。**

一个在你做事的时候插进来问，一个攒到最后一次性汇报。需要我的时机也换了：以前它跑到哪一步我都得盯着，现在是它要问我什么的时候才来叫我。

## 模型通用，细节不通用

把这几件事串起来，我想到的是同一个词：注意力。

模型已经足够通用了，谁都能接到差不多的能力。

**模型这一层的差距，换一版模型就可能被抹平；体验这一层的差距抹不平，只能一点点攒。**

所以这类 agent 工具真正值得打磨的，是那些能省下用户注意力的小细节——给自由设个上限，也是其中一种，用户不必在空白画布上从零开始做决定。

不过有一件事，我到现在也没想明白。

**为什么需要多个 agent 接力？**

这两周我一直用两个 agent 接力，但说实话，我没搞清楚接力本身带来了什么。

是分工吗——一个负责想，一个负责做？是因为不同模型擅长的事本来就不一样？还是只是把等待从一个 agent 摊到了另一个 agent 上（它们都跑在本地，只是不同的进程、不同的 runtime），看起来热闹了一些？

我现在只能确定一点：接力过程中被暴露出来的差异，大部分不在模型身上，而在 harness 怎么处理“不确定”这件事上。至于要不要接力、值不值得接力，我还没想明白。
